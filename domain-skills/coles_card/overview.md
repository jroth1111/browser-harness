# Coles Credit Card Sync

## Scope

Sync the user's own Coles credit card Online Service Centre data into a local
SQLite store:

- current balance and other visible balance figures
- credit card transactions from the transaction-history export when available
- rendered transaction rows as a fallback when export is unavailable
- sync run receipts and blocked-run reasons

Out of scope:

- collecting credentials, cookies, local storage, session storage, auth tokens,
  or MFA secrets
- bypassing Coles/NAB authentication, bot checks, or consent screens
- moving money, changing account settings, making payments, or submitting forms

## Source Surface

Default start URL:

```text
https://secure.coles.com.au/home/account_dashboard
```

Interactive login fallback URL:

```text
https://secure.coles.com.au/login
```

Field-tested on 2026-05-05. The unauthenticated login page is a React/web
component shell. The "Log in with your Coles account" button is inside the
`usl-base-web-shell-landing-page` shadow DOM and is not an anchor.

The login URL is minted by the NAB/USL auth layer:

1. The shell builds a federated auth config with `responseType: "code id_token"`
   and `scope: "openid"`.
2. An auth config interceptor generates a consent id and stores it locally as
   `authorization-key`.
3. The auth strategy calls the DAF foreign-token-management authorisation
   backend.
4. The backend returns `request_url` and `request_params`.
5. The shell navigates to `request_url + "?" + request_params`.

Do not generate standalone OAuth URLs outside the official browser flow. The
post-login callback depends on browser-side state generated by the Coles/NAB
shell.

The script may rewrite the generated Coles Group auth request URL's `max_age`
query parameter to the configured `--auth-max-age` value. The default is `20`
seconds. This is still the official browser flow; it only avoids preserving the
stricter `max_age=0` value when Coles/NAB has generated it.

## Run Contract

1. Open the official Coles account dashboard route in the user's browser
   profile.
2. If login, MFA, CAPTCHA, or account selection is visible, stop unless the user
   requested `--interactive-login`.
3. After the authenticated account surface is visible, extract balances from
   rendered DOM/shadow DOM.
4. Open transaction history through the authenticated app route and import the
   CSV export when available.
5. If export is unavailable, fall back to rendered transaction rows.
6. Upsert normalized rows into SQLite.
7. Record a run receipt with status `ok`, `blocked`, or `error`.

## Database

Default path:

```text
domain-skills/coles_card/.private-data/coles_card.sqlite3
```

Tables:

- `sync_runs` records each attempt.
- `accounts` stores a stable local account key and non-secret account label.
- `balance_snapshots` stores observed balance figures per run.
- `transactions` upserts transactions by account/date/processed-date/
  description/amount hash and stores API/export fields when present:
  merchant name, transaction type, category, account number, card ending,
  pending/posted status, and source method.

## Verification

Use `--dry-run` first after a manual login refresh:

```bash
python3 domain-skills/coles_card/scripts/sync.py --dry-run
```

Then run the persisted sync:

```bash
python3 domain-skills/coles_card/scripts/sync.py
sqlite3 domain-skills/coles_card/.private-data/coles_card.sqlite3 \
  "select status, summary_json from sync_runs order by started_at desc limit 1"
```

To validate the broader export-backed path:

```bash
python3 domain-skills/coles_card/scripts/sync.py --interactive-login --export-csv --require-transactions
```

If selectors drift, inspect the run summary and the current authenticated page.
Do not broaden extraction to hidden storage or auth state.
